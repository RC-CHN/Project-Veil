# 性能、稳定性与抗识别的推进计划

更新：2026-09-16。用户在 Linux 成品双端第一批完成后，提出优先考虑性能、稳定性和匿踪性，并明确混淆要考虑伪装成正常过境业务流量。此前“性能优化暂停”的安排不再作为当前约束。本文是下一阶段建议和待办，不是新增实现或验收结果；engineering2 第一批 goal 已完成，没有自动创建新的执行 goal。

可以从现有正式双端开始工作，无需等待 systemd 安装器或 TUN 全部完成。Linux 全栈目标继续保留，系统接入、证书维护和真实 VPS 验收仍按 [Linux 交付计划](linux-first.zh.md) 补齐。这里的匿踪性指降低协议被流量分析和主动探测区分的能力，不表示隐藏目的 IP 或保证不可识别。

## 已有证据与判断

- 当前 `0.5.0-engineering2` 已完成 24 项成品进程验收，同一 TCP/UDP 持续 260 秒；尚无当前版本吞吐、完整线路开销、弱网、全天耐久或抗识别基线。见 [交付报告](linux-process-report.zh.md)。
- 历史 session16 在 RTT 100 ms、每方向 25 Mbps 条件下，热连接 1 MiB 上传/下载相对 AnyTLS 速度约 56.51%/49.04%，额外流量约 38.56%/39.44%，八组联合门槛 0/8。数据来自被忽略的 `references/veil/docs/v0.5-credit-flow-report.zh.md`，不能当作 engineering2 的实测结果。
- 旧诊断中，较多信用等待发生在本地仍有未交给外层发送的数据时；1 ms 合并减少了一些分批，也增大了部分信用回传等待。应先检查外层发送名额、数据/信用调度和确认路径，现有证据不能认定唯一瓶颈。扩大缓冲或累计字节上限不算解决了这个问题。
- 正式 core 已有部分内部信用、批次、主动等待和执行代次统计；公开状态还未完整接线，node 只有周期快照，没有完整事件归档。历史全天实验中断且存在事件容量不足问题，应先补证据收集和监督能力。
- 当前服务端在 TLS 握手中要求并验证客户端证书。无凭据访问与普通公开 HTTPS 服务可能存在明显差异，需做对应对照；它本身不是 Veil 独有标记，也不能据此直接推断识别率。

## 第一批：让正式版本可测、故障可解释

本批建议作为下一个有界执行目标，先交付测量入口、诊断接线和基线报告，再据此选第一项优化。工具使用实际构建的 veild/veilctl，绑定源码、二进制、配置和模型摘要；保留 engineering2 原始证据，所有新实验写入独立目录。

1. **补有界诊断和事件收集。** 接出已有信用等待、队列/发送名额占用、有效载荷/填充、主动等待、执行代次交接与失败原因；增加必要的 CPU、RSS、goroutine、FD 采样。事件带运行 ID、序号和时间，提供分段文件、磁盘预算、明确的丢失/采集失败状态。日志消费者阻塞、磁盘写满和监督器退出要有可验证行为，诊断不得无限积压或卡住业务。完整性要求未满足的运行不得记为完整验收。
2. **建立正式进程性能入口。** 复用现有独立目标见证和完整载荷校验，增加上传、下载、短交互、持续流、并发混合业务；分别测冷连接和复用连接。先重建旧 RTT 100 ms / 25 Mbps 场景以便对照，再覆盖低延迟、高延迟与丢包条件；明确整形位置、MTU、聚合设置和抓包丢失。限制在自有隔离实验网络，记录工具/权限缺失，不能把回环结果标为弱网结果。
3. **固定比较口径。** 同时运行直连和固定版本 AnyTLS 对照；应用成功以接收端完整校验和最终确认计，不以本地 write 成功计。CPU/内存、并发、数据量、预热、关闭与观察时段保持可比，报告随机交错的重复运行和不确定性。长传输使用显式有限预算，并将预算耗尽用例单列；不能把故意截断误判为性能或网络失败。
4. **测量真实线路成本。** 报告有效吞吐、完成时间与首字节延迟的分布、交互 p95/p99、TCP 重传、UDP 丢失/延迟、CPU/RSS/FD/协程趋势。流量口径固定为双端外链所见的总传输，含握手、双向控制、填充、重传、空闲和关闭；区分应用、TLS/TCP、IP/链路层统计，避免重复计数。内部计数用于归因，不代替抓包。
5. **先做 30–60 分钟稳定性先导。** 混合短流与长流，覆盖执行代次交接、断链、服务端重启、超时取消、预算耗尽、慢目标和诊断输出受阻。每次故障核对数据完整性、错误归因、旧流终止、新流恢复和资源回收；报告恢复时间和预期/非预期失败。长 TCP 已断时不得宣称透明续传。

profiling 采用明确开启的限时本地采集，CPU、分配、block/mutex、trace 分别用于对应问题；测量开启和关闭诊断的差异。Go 官方说明 profiling 有开销且多种工具会互相干扰，因此正式速度成绩与高开销诊断运行分开记录。[Go diagnostics](https://go.dev/doc/diagnostics)

本批完成标准：可以重复运行正式双端的性能和故障实验；双端事件、目标见证和线路字节可核对；有当前版本结果、资源趋势、未解释失败以及下一项干预的依据。没有当前证据前不承诺吞吐提升幅度。

## 第二批：每次解决一个已测得的瓶颈

优先顺序随第一批结果调整，初始候选如下：

| 候选方向 | 需要先确认的现象 | 改动边界 |
|---|---|---|
| 信用与发送调度 | 数据在本地排队，但窗口或外层名额被其他工作占用；信用到达后仍不能及时使用 | 在模型允许的发送机会内改进分配和公平性，控制/FIN 不饥饿；保留消费确认与外层收据的区别 |
| 短交互与复用 | 建立承载、OPEN、代次交接或排队占据主要时间 | 复用已有承载、减少无效等待，保持连接/OPEN/寿命预算和正确关闭 |
| 实现开销 | pprof/trace 显示分配复制、锁竞争、定时器或唤醒占据显著成本 | 先做局部改动，避免依赖 amd64 特定优化或无限缓存；在低资源配置下复核 |
| 模型与线路成本 | 在实现瓶颈减轻后仍受协议往返或模型容量限制 | 作为独立模型/协议实验，保留旧版本；联合评估速度、开销和可识别特征 |

每个候选独立提交，比较相同基线与多次重复结果，保留被否定的假设和失败记录。正确性、认证、目的地策略、资源上限或稳定性回归时不合入候选；速度收益若改变线路行为，则必须补对应抗识别比较。更大的缓冲、更多连接、提前确认和削减模型约束不能悄悄混入“同条件优化”。

历史目标继续保留：同语义下约 80% AnyTLS 速度、已声明工作负载的总额外流量 20–40%、约 30 ms 主动等待预算。它们仍未达标；短流、冷启动和长流分开报告，不能用大文件平均值遮盖短流成本。若目标相互冲突，应报告取舍并重新讨论，不能改统计口径制造通过。

## 抗识别：以正常过境业务为对照

用户明确要求考虑伪装成**正常过境的业务流量**。因此对照应来自目标使用环境中实际跨境的正常业务，不能只选任意 HTTPS、境内低延迟流量或本机回环样本。需要固定观察点，并记录客户端网络/地区、境外服务托管环境、链路条件与采样时间；尚无真实跨境环境时，本地实验只能用于实现筛查，不能据此认定正常过境伪装成立。

初始建议研究真实的文件同步/对象传输客户端：它与现有对象交换结构相近，可覆盖短元数据交互、分批上传下载、回执、空闲及恢复。API 交互可作另一个业务类别；网页浏览、文件同步和持续视频应分别建模和评价，不能把互不相关的特征随机拼成一个“正常流量”。这些只是候选，最终选择必须有自有或获授权的正常业务语料支持。目前尚未证明现有模型接近任何一种实际过境业务。

正常业务对照与 Veil 样本应尽量匹配链路和托管条件，覆盖以下约束：

| 层次 | 需要一致或有证据解释的行为 |
|---|---|
| 服务部署 | 目的 IP/网络归属、端口、托管方式、域名/SNI 或无 SNI 的使用方式、主动访问可见的证书与服务行为；普通 VPS 与 CDN 服务的差异需单列分析 |
| 客户端与握手 | 实际客户端类型、TLS 协商和复用习惯；不能仅换 ClientHello 就宣称成为浏览器或真实同步客户端 |
| 业务因果关系 | 元数据/控制交互、上传与确认、下载请求与返回、失败重试的先后关系；模型应表达业务过程，不能只匹配独立包长分布 |
| 完整会话 | 上下行比例、突发与间隔、吞吐随网络变化、空闲、连接寿命与正常结束；分别核对短交互、批量传输和混合负载 |
| 长期使用 | 多连接之间的节奏、日常重复行为及模型代次切换是否形成额外规律；短前缀看似正常不能替代长期检查 |

域名继续可选，不因研究伪装而擅自改变公网 IP 证书优先策略；但必须验证这种部署形态在所选正常业务中是否有合理对照。线路行为模型无法改变 VPS 的网络归属，也不能靠填充抹去所有部署差异。源/目的 IP、证书身份等特征单独分析，既保留现实观察者可见信息，也避免检测器仅记住实验专用 IP 就被误报为识别了协议。

业务数据应装入模型允许的容量和交互，不应让应用每一次 write 直接决定一次外层发送。选定真实业务后再校准容量、等待和填充预算，并在不同负载下复核；若大流量迫使模型明显偏离业务分布，应报告可用范围和成本，不能无限加填充或把异常行为纳入正常标签。

可编程行为模型方向已有 Marionette 等研究；可编程本身不是当前实现抗识别有效的证据。[Marionette, USENIX Security 2015](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/dyer)

评估分三层，均使用当前正式二进制：

- **被动单连接：** 握手特征、可观察 TLS 记录与包长、方向、时序、突发、空闲和关闭；分别评价启动前缀与完整会话。HTTP/2 细节只能通过授权端点解密诊断，不能当作被动观察者直接看到的字段。
- **跨连接：** 同一端点多次会话的连接数量、复用、寿命、执行代次节奏和其他重复规律；与对应正常业务比较。
- **主动探测：** 对自有端点测试无客户端证书、错误身份、普通 HTTPS 请求及不完整/异常握手的表现，比较匹配的正常服务。TLS 1.3 的 CertificateRequest 在 ServerHello 之后已加密；被动观察不能直接读取它，主动连接方则能观察自身握手与服务行为。[RFC 8446 §4.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.3)

先审计当前 mTLS 入口是否符合选定的过境业务。若选择真实使用 mTLS 的业务客户端，需要该类正常流量作为对照，不能只凭“存在 mTLS 服务”就推断隐蔽。若目标是普通公开 HTTPS 服务，单加网页、随机填充或改 ClientHello 不足以解决握手认证差异；需要单独设计凭据持有者入口与真实公共服务的关系，保持未授权者无法使用代理。此类改变涉及认证和协议边界，不混入性能小修。

检测数据按独立运行、端点、时间/网络和模型种子划分训练与留出，避免同一会话的包分别落到两边。正常集同时包括选定业务和其他真实正常过境业务，按业务类别、链路和负载分层报告。冻结评估流程，包含简单统计特征基线；每个重要候选在独立训练数据上重新训练检测器，再在留出数据比较，避免只针对旧检测器调参。报告固定误报率下检出率、样本量和置信区间；样本不足时不宣称低误报率结论。证据只覆盖声明的观察者和数据集，不等价于现实网络保证。

## 稳定性放大与 Linux 全栈衔接

先导通过后，再做带完整监督的 2 小时和独立 24 小时运行，检查资源是否持续增长、取消/关闭是否回收、网络故障后的新业务恢复时间和业务完整性。执行代次交接由计数证明，不能仅凭运行超过 240 秒推断通过。TUN/DNS、换证和升级的恢复实验随相应功能接入补齐，不把尚未实现的功能列为已测项目。

验证按回环、隔离弱网、真实受控 Linux 双机三层分别报告。真实 VPS 环境尚未确定，当前先完成本地可重复部分。安装与服务管理继续作为后续交付工作；systemd 只是适配层，core/node 保持前台运行，低资源检查、日志预算和有限队列为将来 OpenWrt 留出空间。交叉构建不代替 OpenWrt 原生验收。
