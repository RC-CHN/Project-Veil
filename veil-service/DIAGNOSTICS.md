# 连接诊断

桌面、LuCI 和 OPNsense 的连接卡片提供“更多 → 诊断”。首先点“测试 Google”确认当前完整路径是否可用，再查看对应时间的错误。启动状态仅表示本地代理入口已监听；历史错误不代表当前仍然断线。

诊断面板分别展示出口隧道和本机管理的中转隧道：运行开始时间、当前入口连接数、每个入口的连接上限、活动业务流、拒绝数，以及物理隧道池的总数、空闲数和拨号状态。停止连接后仍可查看本次运行的记录，重新启动会开始新的一次统计。

每一层保留最近 16 组错误。连续相同的错误合并，显示首次时间、最近时间和次数。错误按连接服务器、TLS 握手、认证、打开目标、读写隧道等阶段区分。数据只在请求完成或出错时更新，不记录代理内容，也不按数据包写日志。

命令行与导出 JSON 的 `diagnostics.pool.draining` 表示已停止接收新流、正在等待已有流结束的物理连接数，零值可省略。核心等待 OPEN 回复或 DONE 确认超时后会排空相应连接，让后续请求改走其他连接；已有业务流继续按原来的生命周期和超时运行。调用方取消、明确的远端目标拨号错误不会触发排空。排空数量包含在 `pool.total` 内，仍受连接数上限约束。

`diagnostics.pool.retry_after_ms` 表示 TCP/TLS 建连失败后的剩余退避时间，零值可省略。退避期间已有连接仍可使用；没有可用连接时，请求快速返回最近一次建连错误，所以错误数不等于实际拨号次数。退避首轮为随机 100–200 ms，连续失败逐步增加至最多 1–2 s，成功建连后清除。后续业务请求推动重试，没有后台探测流量。

`diagnostics.pool.dial_attempts` 记录实际物理拨号次数；`open_retries` 记录已复用隧道在 OPENED 前失效后触发的单次替换次数。只有尚未向应用交付流、尚未发送应用 DATA 时才可替换；不会重放进行中的请求，也不会自动重试明确的目标拒绝、鉴权失败或仍存活会话上的 OPEN 超时。两个计数随实例重建归零。

## 收集一次故障

1. 记下故障时间和正在使用的代理入口，先导出诊断，再考虑重启。
2. 测试同一条完整连接。记录它是立即失败、超时，还是第二次请求恢复。
3. 比较出口层与中转层的错误时间。中转层的 `tunnel dial` / `TLS handshake` 失败指向本机到中转服务器；出口层同阶段失败可能来自中转到出口、出口握手或其伪装站点依赖。阶段是定位线索，不足以单独证明网络阻断。
4. 对照中转和出口服务器同一时刻的日志。客户端诊断不是远程日志，服务器会独立记录认证、目标拨号和转发失败。

导出的 JSON 包含服务器地址、入口、时间和网络错误，不包含认证密钥或连接配置。对外分享前仍应检查地址是否需要脱敏。

## 命令行与服务日志

多连接客户端：

```sh
veilctl -socket /var/run/veil/control.sock connections
veilctl -socket /var/run/veil/control.sock -id la connection_test
```

单实例服务器使用其实际控制套接字：

```sh
veilctl -socket /run/veil-losangeles/control.sock status
journalctl -u veil@losangeles --since '10 minutes ago' --no-pager
```

OpenWrt：

```sh
logread -e veild
```

OPNsense 可从 Veil 服务日志及插件诊断面板读取记录；Windows/Linux 桌面从连接卡片导出同一格式的诊断。

`veild` 每 5 秒将新增错误与状态变化写入标准错误，由 systemd、procd 或 rc.d 的日志配置保存。日志内包含 `connection_id`、`hop`、`started_at`、错误序号、时间和阶段。`hop=relay` 表示此连接使用的本地中转客户端，`hop=endpoint` 表示当前实例自身。合并错误的 `count` 为该组累计次数，不应把不同日志行中的它重复相加。最多保留 16 组的内存记录可能在密集故障时淘汰旧组，应同时保留系统日志。服务退出前会做最后一次采样，进程被强制杀死前尚未采样的数据可能丢失。

常见线索：

| 现象 | 下一步 |
| --- | --- |
| `connection_limit` / 拒绝数上涨 | 对照活动入口连接数和上限，检查应用并发与未结束连接 |
| `tunnel dial` 超时 | 检查对应服务器端口、路由和 TCP 重传 |
| `TLS handshake` 失败 | 对照两端时间、认证配置、TLS/REALITY 参数以及服务端伪装站点连通性 |
| `open target` / `target dial` | 检查出口侧 DNS、目标端口和目标站点 |
| `write_stall` | 已有数据等待转发且持续无进展；结合 send/receive 区分本地背压与隧道阻塞 |
| `idle_timeout` | 查看发送/接收方向在等待什么，区分真正空闲和链路无响应 |
| `stream_reset` | 对照另一端更早的错误；reset 本身只是该业务流被关闭 |

指标从每次运行开始累计，入口连接数、业务流数和物理隧道数分别对应不同对象，不应将它们直接相减推断丢失连接。
