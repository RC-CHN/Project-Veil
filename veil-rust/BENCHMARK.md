# Rust 与 Go 数据路径实测

日期：2026-09-29。基线：Go `a307dbb`，`batch` 构建；Rust 为本目录实验实现。

结论：这版 Rust 的优势主要是短请求延迟和常见场景的内存占用；8 流大吞吐落后于现有 Go 优化版。本轮结果不支持整体替换 Go，也不证明 Rust 语言本身更快或更慢。

## 条件与范围

- 本机 Linux 7.0.0-34-generic / Intel Xeon CPU Max 9470C，环回 TCP；不是公网线路测速。
- 服务端固定 CPU 14，客户端 CPU 15，目标 CPU 16，负载 CPU 17；四个独立物理核，同 NUMA 节点。代理各用一核；Go `GOMAXPROCS=1`，Rust Tokio 单线程。
- Rust 1.96.0，`--release`、thin LTO；rustls 0.23.45 / ring 0.17.14 / Tokio 1.53.1。Go 使用现有 TLS 批处理优化，额外测 Go OpenSSL 服务端。
- 标准 TLS 1.3 / AES-128-GCM，双方关闭 TLS 填充；相同随机范围和双通道连接池策略。1 流实测 1 个物理会话，8 流实测 2 个物理会话。
- 每组大流传输合计 2 GiB（8 流分摊总量），短请求 5000 次；5 次重复、固定随机种子打乱执行顺序，共 150 组。表格使用五轮中位数。
- TLS 握手和预热不计入测量。Go/Go 保留默认混合密钥交换，含 Rust 的组合使用 X25519；因此本轮不能比较冷握手性能。
- `perf stat` 单独测量两个代理的 task-clock、cycles、instructions；CPU 效率分母为两端 CPU 时间之和。负载发生器和目标的 CPU 不在分母里。
- CPU 频率未锁定，使用共享测试主机；报告完整范围，不把几个百分点的差距当成普遍结论。

## 正确性与行为边界

14 个测试通过，包括 3 个固定格式/认证测试、10 个复用边界测试和 1 个真实进程互通矩阵。矩阵涵盖 Rust→Go、Go→Rust、Rust→Rust：12 MiB 内容与流控、24 条并发连接、拒绝后的继续复用、错误 AUTH、上游进程退出及重连。Rust 客户端另测 HTTP CONNECT 和错误主机名拒绝。

复用测试覆盖双向半关闭的两种顺序、零额度流不阻塞其他流、部分 DATA 立即可读、窗口溢出、非法状态、截断与物理 EOF、双 FIN 后缺少 DONE，以及空唤醒不消耗启动切分次数。

可观察差异：Rust 前端在隧道异常时设置 TCP reset；当前 Go 前端及时关闭本地 socket，但可能呈现 EOF。两者在杀死上游测试中都及时结束并能建立新会话。Go 源码未在本轮修改。

本实现是 Veil v0.3/T。尚未实现 R 档位、浏览器模板和 TLS 记录填充；普通 HTTP absolute-form 转发也不在此实验里。没有进行抗识别、真实 WAN、ARM、多核扩展或冷握手验收，不能把本表当作这些场景的结论。

## 判断与后续优化方向

保留 Go 为主实现。Rust 已经具有可单独运行、可互通、能受控测试的核心，但还没有展示全面性能优势。下一步若继续投入，优先分析 8 流场景的帧缓冲分配、复制、唤醒和 TLS 批量 I/O；这些是源码中可检查的优化候选，不是本轮已经通过热点采样证明的瓶颈。应先解决该场景的损失，再评估迁移 REALITY 与现有随机化发送策略的工作量。
